# Signing up for a site

ClearOps can create an account for Paul on a site he names in chat. It is never autonomous: a sign-up
is two steps and the second is his. This is the third gate of the same shape as the executive
assistant's send gate (`docs/` and README, "Sending email, inviting and cancelling") and the DNS gate
(`docs/GODADDY.md`).

- `src/signup.ts`: the rules, the one thing that fills and submits a form, the log.
- `src/signup-gate.ts`: the gate itself, the preview Paul sees, the `signup apply <id>` parser and the
  preparing worker's only tool, `signup_prepare`.
- `test/signup.test.ts`: offline tests (a fake browser session, a fake submitter, a real vault in a
  temporary folder). No live network.

## How it works

1. **Prepare.** Paul asks in chat ("register me on suno.com", "make me an account on X"). The chief
   starts a job of a kind that carries the browser (`research`, `ideate`, `advisor`, `prebid`) with the
   `signup` permit, and that job reads the site's own sign-up page and calls `signup_prepare`. It may
   only prepare. The service, not the model, then applies the rules and posts the exact plan in Paul's
   chat: the site, the email address to be used, every detail that would be filled in, a link to the
   site's terms, why, and an id. Nothing is filled in.
2. **Approve.** Paul replies `signup apply <id>` (`signup cancel <id>` cancels). The orchestrator
   matches that whole message after the allowlist check and before any model runs, so no email, web
   page, job output or upload can produce it. Only then does the service open the sign-up page, check
   the plan again (a hash of exactly what Paul saw, plus the rules), generate the password, fill the
   form and submit it.
3. **Store.** On success the login goes straight into the vault (`src/vault.ts`): site, username,
   password, and later agents can sign it in. The password is generated by the service, never asked of
   Paul, and never appears in chat, in a log or in a job output.

## Configuration

| Variable | Meaning |
|---|---|
| `SIGNUP_EMAILS` | The addresses Paul named for sign-ups, comma separated. **With none set, no sign-up can be prepared at all.** This is the safe default: the service never invents an address or takes one from a page. |
| `SIGNUP_SITES` | Extra domains where a sign-up may be prepared, on top of the sites agents may already act on (`src/site-policy.ts`). The never-list still blocks money sites, email providers, Microsoft, password managers, government identity services and this service's own infrastructure, whatever is set here. |
| `SIGNUP_TTL_HOURS` | How long a prepared sign-up waits for approval. Default 6. |
| `SIGNUP_DAILY_CAP` | Most sign-ups approved per Europe/London day. Default 3. |

The address is checked against `SIGNUP_EMAILS`; the site must be one Paul has allowed (the act list,
the vault, or `SIGNUP_SITES`); and a site that already has a login in the vault is refused as a
duplicate. Nothing is opened by default: a site still has to be allowed by Paul, and every account
still has to be approved by him.

## What is never done, whatever anyone says

These are in the code, and Paul's approval of one plan never authorises another. A page, an email, a
job output, an upload or the plan itself cannot talk past them.

- Never pay, never enter card, bank or billing details, never start a paid trial that needs them. A
  sign-up page or a field that asks for any of those stops the whole thing and hands it back to Paul.
- Never do phone, identity, government or age verification: that step is Paul's.
- Never create or change an account on a money site, an email provider, Microsoft, a password
  manager, a government identity service or this workforce's own infrastructure (`NEVER_SITES`).
- Never register Paul anywhere he did not name in chat, and never allow a site because a job, a page
  or an email asked for it.
- Never a second account where a login is already stored.
- Never change a password, recovery address, 2FA setting or contact detail on an existing account, and
  never delete an account: this code has no route to any of those.
- Never post, comment or publish as him. The submit control has to be a sign-up control, and anything
  consequential (pay, send, post, publish, delete, close account) is refused.

## Email verification

A site that wants the address confirmed is normal: the account is created and Paul is told to watch
for a message. The executive assistant can read that mail (read only) and a follow-up job may open the
link, but only on the sign-up site's own address. Replying to it, forwarding it or sending anything is
never done. If verification needs a phone number or an identity document, the service stops and tells
Paul: that part is his.

## The record

One JSON line per event (`prepared`, `cancelled`, `stopped`, `applied`, `failed`) is appended to
`DATA_DIR/signup/actions.log`, owner-only, and the store keeps the sign-up itself (site, url, address,
fields, hash, who approved and when, what the site said). Neither carries the password. `/pending`
lists what is waiting, with the same preview Paul was shown.

## Paul's decisions

- Which address (or addresses) to use for sign-ups: `SIGNUP_EMAILS`. Until he names one, every
  sign-up is refused with a sentence saying exactly that.
- How he wants to hear about a site that needs payment, a phone number or an identity: today the
  service stops, says so in chat and stores it as `needsPaul`; the account is not created.
